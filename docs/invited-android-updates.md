# Android 受邀应用内更新

本阶段不开放官网 APK 下载、二维码或公众注册。Android 更新改为登录后的受保护接口，保留现有长期签名、应用身份、安装前确认和默认关闭的自动下载。受限分发不替代备案要求，不据此声明备案豁免。

## 接口与授权

- 清单：`https://plan.zijun701.cn/api/client-updates/android/latest`
- APK：`https://plan.zijun701.cn/api/client-updates/android/releases/{versionCode}/apk`

两者均要求有效 Bearer access token，且账号仍存在。生产注册关闭，现有成员由管理员邀请；普通成员和管理员均可使用。将来若开放公众注册，需要重新决定更新资格策略，不能直接沿用本次“现有账号均受邀”的条件。

前端通过现有会话刷新机制检查当前身份，只将短期 access token 交给 Android 更新通道；不传 refresh cookie，不写 token 到清单或下载 URL。原生再次核对固定更新源、当前业务服务器和账号；不同域、端口、公共文件路径、重定向均拒绝。下载使用独立工作线程，仍校验大小、SHA-256、包名、版本和已安装应用证书，安装前再校验一次。

清单与 APK 返回 `Cache-Control: private, no-store`。私有目录只挂载到后端，不挂载到 Web/Nginx。官网 `downloads/manifest.json` 保持 `android=null`，原静态 Android 清单和公共 APK 路径保持 404。未登录请求受保护接口返回 401。

## 用户行为

联网登录当前云端账号后可检查更新。普通更新可稍后处理；自动下载默认关闭，需本人勾选，受限 Android 的偏好按服务器与账号绑定。登出或换服务器不会沿用此前账号的更新提示和可安装状态。下载完成不等于安装：本人保存编辑后确认，再通过 Android 系统安装提示。同包名同签名升级，不卸载、不清数据。

必要更新仍由 `minimumSupportedVersionCode` 明确决定，不能因为版本号变动就强制升级。强制策略按当前构建和账号隔离；不能用旧账号的策略限制新账号。未经实际下载安装验证，不标记真机通过。

## 维护者流程

1. 同步版本及递增 Android 构建号，运行版本校验和回归测试。
2. 用 `scripts/prepare-formal-clients.ps1` 构建独立候选包，沿用原证书。
3. 将真实发布说明保存为文本文件；运行 `node scripts/prepare-invited-android-release.mjs <候选目录> <说明文件> [最低构建号]`。默认最低构建号为 1，即可选更新。工具重新核验 APK 签名和候选哈希，仅生成被 Git 忽略的私有阶段目录。
4. 先部署包含鉴权接口的后端。云端升级使用 `production-compose.sh` 保留 Windows 静态下载、时区及 Android 私有挂载，不修改数据库结构或原客户端数据。
5. 运行 `powershell -File scripts/publish-invited-android.ps1 -StageDirectory <私有阶段目录>`。上传校验后启用私有源；使用两个专用受邀普通账号核对实际清单、账号绑定、APK 哈希及公开下载仍关闭。鉴权核验失败恢复先前私有源，保留新 APK 和数据库。
6. 实机执行应用内下载安装验收，记录升级前后账号、三模式、休息日和队列。生成最终发布记录并推送源码；GitHub 公共附件仍限 Windows，不上传私测 APK、账号或任何凭据。

远端 APK 按构建号不可变保留；仅 `current.json` 原子切换到新版本。该次发布的私有 staging 中保留 `rollback.sh`，回滚恢复更新配置，不降级安装客户端或清理数据库。
